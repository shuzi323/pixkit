## PixKit — 纯前端图片工具站（从零搭建）

用户诉求："做一个能自动赚钱的项目"。经过方案确认，选择"在线工具站"路线，用户已有域名和服务器。

### 技术选型
- **零构建纯前端**：原生 HTML + ES Module，无 React/Vite/webpack。理由：工具站首屏速度和可靠性优先，扔到任何服务器即可运行。
- **零运行时依赖**：未引入 JSZip 等库，ZIP 打包手写在 `assets/js/common.js`（store 模式，约 100 行，含 CRC32 表）。
- 共享引擎：`compress.js` 同时驱动压缩 / 格式转换 / 改尺寸三个页面，初始参数从 DOM 控件的 value 读取（不硬编码在 JS 里），所以同一份代码配不同 HTML 默认值即可复用。

### 踩坑记录（重要）
1. **OffscreenCanvas 必须先 getContext 才能 convertToBlob**，否则抛 "The OffscreenCanvas has no rendering context"。这导致最初 `canEncode()` 把全部格式判定为不支持，PNG 走了错误分支。修复在 `canEncode` 里先取 2D context。
   - 注意：不要在 `makeCanvas()` 里预取 context，否则后续 `getContext('2d', {alpha:...})` 的参数会被忽略。
2. **headless Chrome 拦截 `a[download]` 下载**，`Page.setDownloadBehavior` 无效。改用 hook `HTMLAnchorElement.prototype.click`，从 blob URL 读回图片验证真实像素尺寸。
3. 重编码后可能比原图更大（PNG→PNG、已高度压缩的 JPEG）。处理：同格式或「自动」模式下且尺寸未变时，退回原文件。

### 产品判断（写下来供后续参考）
- 证件照工具**刻意不做 AI 抠图换背景**。人像边缘（碎发）质量不可控，证件照对边缘瑕疵零容忍，与其交付半成品不如明确说明。已在页面文案中如实交代。
- 首页曾出现「自动抠图换背景」的不实描述，已改正 —— 产品文案不能承诺做不到的事。
- README 里对收入预期写得很保守：工具站收入完全取决于流量，1 万 PV/月约几十到两百元。不做「躺赚」式表述。

### 验证结果
- 压缩：3.2MB → 1.4MB（质量 80），目标 200KB 模式全部落在 179–189KB。
- 证件照：二寸导出 413×579px，排版 1795×1205px（6 寸 @300dpi）共 8 张，均匀居中。
- 全站链接零 404。

## 补充：Cloudflare Pages 部署配套

用户问「怎么部署到 Cloudflare Pages，需要域名吗」。调研结论：

- **不需要域名**，免费送 `*.pages.dev`。
- **但 `pages.dev` / `workers.dev` 在国内不稳定**：自 2022 年起常遭 DNS 污染，部分运营商/时段解析到 `127.0.0.1`。绑自定义域名可明显改善（绕开该域名层污染）。
- **Cloudflare 无中国大陆节点**，绑域名后延迟仍 200–300ms。官方 FAQ 明确 Pages 在大陆不可用。境内节点（China Network）只对企业版且需 ICP 备案。
- 结论建议：先用 Pages 快速上线验证，若确认流量主要来自国内再迁回自建服务器。纯静态站迁移成本近乎为零。

### 为此新增的文件
| 文件 | 作用 |
|---|---|
| `scripts/build-dist.mjs` | 生成干净 `dist/`（13 文件 / 104 KB），排除 node_modules、tests、.workbuddy |
| `_headers` | Cloudflare Pages 响应头：HTML 不缓存、assets 缓存 1 天、基础安全头。**故意不配 CSP**（页面有内联样式和 data: URI 图标，配不好会直接搞坏站点） |
| package.json scripts | `dev` / `dist` / `deploy`（wrangler）/ `test` |

### 两个部署坑（写进 README）
1. 必须**先在 Pages 后台添加自定义域名，再配 DNS**，反过来会 522。
2. 域名若有 CAA 记录，需放行 `letsencrypt.org`、`pki.goog`、`ssl.com`，否则证书签不下来。
3. canonical 要填**自定义域名**而非 `pages.dev`，否则 SEO 权重记到 pages.dev 上。

### EXIF 无损删除的实现要点（值得记住）
JPEG 是分段结构：`FFE1`(APP1) 装 EXIF、`FFED`(APP13) 装 IPTC、`FFFE`(COM) 装注释，
`FFDA`(SOS) 之后才是压缩图像数据。清除时只摘掉前三种段、把 SOS 之后**原样搬运**，
不经过 canvas 重编码 → 画质零损失。

测试里用「尾部 2 万字节逐字节比对」来证明这一点（`origTail.equals(cleanTail)`），
比单纯对比文件大小更可靠。

### 调试记录
- 手写 EXIF 测试数据时踩了两次坑：① 只构造了 GPS 纬度没构造经度，解析器要求两者齐备才返回；
  ② `Buffer.alloc(160)` 不够写 184 字节的 TIFF。都是测试数据问题，不是产品代码 bug。
- 三个工具最初都忘了隐藏 dropzone，导致上传后上传区还挂在上方。统一加了「换一张」按钮。
